最新状态：按用户最新要求使用Python3.12、MuJoCo3.17.0；fast-render作用于相机、窗口和视频，会改变感知图像。前墙检查目标和速度调整后两次复测通过死胡同，见 `docs/DEAD_END_TUNING.md`。下文3.10回退、相机撤回描述及速度数据均为历史记录。

## WSL2 / RTX 5060 本地性能修复（2026-11-16）

窗口同步现在同时受真实时间和仿真时间限频，下一真实时间期限从同步完成后计算；渲染落后时丢弃过期显示帧，避免每个2ms物理步都重复刷新。新增 summary.timing_p95_seconds.viewer_sync。

可选 `--fast-render` 现在只关闭窗口及俯视视频中的阴影/反射，传感器相机保持原始渲染。此前曾同时作用于传感器图像，会改变感知输入；死胡同回归审查中已撤回这一部分，新增传感器图像、点云及物理终态一致性测试。不能把此前修改称为纯显示优化，也不能用10秒短测证明死胡同长路线通过。

下述14.230秒性能数据来自撤回前的相机快速渲染版本，不能作为当前版本的性能结果。当前死胡同回归仍在审查，参见 `docs/VERSION_AUDIT.md`。

本机 Ubuntu24.04 WSL2、Python3.10.22、MuJoCo3.17、D3D12 RTX5060：原15Hz窗口2sim/39.411wall、275次同步；修复同步后10sim/27.686wall；再启用快速渲染，最终独立启动脚本实测10sim/14.230wall，102次同步、94次前视相机更新，0诊断障碍接触、未跌倒。前后短测长度不同，不作为整圈倍速或稳定实时保证。最终证据在本地 `output/wsl-setup/perf-final-solo/`。并发运行pytest时同样10sim耗时22.552wall，因此计时不要同时开多个仿真或测试。

Windows启动脚本 `/mnt/d/Desktop/Mujuco/start-simulation.sh` 使用 D3D12、15Hz窗口和 `--fast-render`。之前按未修复循环启动的进程需要退出并重启。119项测试通过（61.90s），包含慢窗口回归测试及两种画质下的球/终点识别；769项原始资源校验通过。本轮未执行完整路线或实物测试。

2026-11-15。普通运行默认不录屏，不输出视频、图片/地图快照、物理NPZ、原始传感器记录，也不导出约64MB的运行场景副本。保留小型配置/场景来源/路线、终端诊断、trajectory和summary，以便定位停车原因；旧输出不删除。

```bash
.venv/bin/go2-rescue mujoco --viewer --realtime --task-fixture --seconds 600 --output "output/run-$(date +%Y%m%d-%H%M%S)"
```

需要诊断归档时分别显式添加：`--video`视频；`--record`原始RGB/雷达；`--save-physics`采样物理状态及本地场景；`--snapshots`地图/图片快照及本地场景。`--record`不再隐含视频；没有任何默认录制。相机仍为导航生成10Hz观测，关闭录屏不能关闭导航所需传感器。

物理步进、凸MPC、定位/建图/规划和OpenCV感知使用CPU。相机/窗口通过OpenGL渲染，启动日志和summary显示实际GL_RENDERER；本机实测NVIDIA GeForce RTX3060 Laptop GPU，不能把GPU占用率解释为MPC在CUDA上求解。

此前窗口只在10Hz录像循环sync，并重复渲染一次前视相机、编码960×480视频，还把所有带图像Frame留在内存。现在窗口独立同步（默认上限60Hz，`--viewer-fps`可调1～120），录像按需创建并复用最近相机图；Frame改为计数，耗时统计使用有界队列。小型矩阵BLAS线程限制为1，退出恢复；稀疏地面列的下包络中位数按列长度批量计算，保留原数值语义。

用户两份fast日志均停在S_curve第4检查点：`ordered_align_checkpoint`、全零速度，未跌倒，最后由用户关闭窗口。提速后到原点时朝向未对齐，转动扫描被墙面拒绝，小目标区域也找不到恢复姿态。路线先验把该转向位置提前25厘米到转向区，不修改官方地图。检查转向的1.5秒范围不再超过所需最终朝向。返回后的标记窄口恢复2厘米额外余量；完整物理车身、地面、净空、水面及制动检查不变。
